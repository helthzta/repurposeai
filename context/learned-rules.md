## Rules learned so far

<!-- Format:
R-001 · <rule> · <why, ≤10 words>
-->
R-001 · When a `VideoProvider`'s output URL needs auth to fetch, return it via `PollResult.outputHeaders`, not by baking creds into the URL · `mirrorToStorage` threads headers through; keeps provider swaps to one file.
R-002 · Never mirror an intermediate/non-deliverable asset into `generated-videos` under the user's own path · that bucket's RLS lets the owner read anything under their prefix directly, not just app-linked files — re-fetch from the provider instead.
R-003 · A provider's single-call duration cap belongs on `VideoProvider.maxClipDurationSeconds`, not hardcoded in `generation.ts` · keeps the provider-agnostic guard (reject > cap) per architecture invariant #5; used for chaining until that was removed, now for rejecting unsupported durations.
R-004 · When a user's shorthand product note lists fields/config to change, check what's read downstream before dropping anything not mentioned · shorthand notes are rarely exhaustive; ask (see D-002) rather than silently breaking a dependent feature.
R-005 · Prefer removing a DB column's *usage* over a destructive migration when a table might hold real user rows · `brand_profiles.tone`/`cta` left in schema, unused, rather than dropped (D-001).
R-006 · Tone and CTA are always AI-derived from the analyzed video, never manual input · user wants zero config, video already implies the answer.
R-007 · Keep any `video_analyses`/`brand_profiles` field a shipped feature depends on, even if a rewrite note omits it · shorthand notes aren't exhaustive; dropping breaks dependents silently.
R-008 · The Ideas-step (concepts → pick → script) flow only replaces the dashboard UI, not `generateScripts` used by the public v1 API · v1 runs synchronously with no human to pick an idea.
R-009 · "Original" camera style passes the analyzed `visual_style` text directly into the video-gen prompt · reuses captured-but-unused data over a generic instruction.
R-010 · `withLogger()` applies a baseline per-IP rate limit to every route by default; pass a tighter `{ rateLimit }` option for AI-calling/costly endpoints · keeps rate limiting enforceable in one place instead of per-file.
R-011 · Admin cross-user queries must go through `requireAdmin()` (checks the caller's own `is_admin` via the RLS-scoped client, only then hands back the service-role client) · never let a non-admin session query other users' rows directly.
R-012 · "Credits spent" in the admin dashboard sums `generations.credits_charged` for `completed` generations only, not `credit_transactions` net of refunds · simple and accurate for completed jobs; revisit if precise net-spend accounting matters later.
R-015 · Any server-side `fetch(url)` that's supposed to return a video (`/api/v1/commercials`) must check the response `content-type` starts with `video/` before trusting it · a YouTube/webpage link returns `text/html` with a 200, which silently corrupts the source row until Gemini rejects it at analysis time with an opaque error — validate at ingestion, not just at use.
R-016 · `brand_profiles` is user-owned and reusable (`user_id`, `label`, `is_default`), not one-row-per-project · projects reference one via `projects.brand_profile_id`; fetch a project's brand via `requireProjectBrand()` in `src/lib/projects.ts`, not a direct `brand_profiles.eq("project_id", ...)` query (that column no longer exists as of `0019`).
R-017 · "Only one default brand profile per user" is enforced in application code (unset-then-set in `PATCH /api/brand-profiles/[id]`), not a DB constraint · avoids a trigger for a soft invariant; add a partial unique index if it ever proves too weak.
R-018 · `brand-logos` storage paths are `{user_id}/{brand_profile_id}/{filename}`, not `{user_id}/{project_id}/{filename}` · brand profiles aren't project-scoped; safe because that bucket's RLS only checks the first path segment against `auth.uid()`, never the second.
R-019 · The API-keys UI is intentionally removed (nav/`/api` page/Settings) while the backend (`api_keys` table, `/api/v1/commercials`) stays live · "not needed" meant hide the surface, not delete the public API.
R-020 · Sign In (`/login`) and Sign Up (`/signup`) are separate screens (superseded the earlier unified-form decision) — Sign Up collects a username, Sign In doesn't, no auto-fallback between them · explicit user request; both share `src/components/auth/AuthCard.tsx` for chrome to avoid duplicating the visual shell.
R-022 · Both auth screens' `page.tsx` check `getUser()` server-side and `redirect("/dashboard")` if already signed in · a logged-in visitor's session persists — they should never be shown the sign-in/sign-up form again, not just silently allowed past it.
R-035 · "Video Link" upload mode (paste a URL instead of uploading, `/api/uploads/from-link`, superseded R-014/R-021) was removed from the dashboard `UploadStep.tsx` — file upload only now · explicit user request, "only user can upload files"; the public v1 API's own URL-based ingestion (`/api/v1/commercials`) is untouched, it's a separate code path (see R-008, R-019).
R-023 · When a migration drops a column an existing RLS policy references, drop (and recreate, if still needed) that policy *before* the `drop column` statement, not after · Postgres refuses `alter table ... drop column` while any policy still depends on it (`0019`'s first apply attempt failed this way — fixed by reordering, not by adding `cascade`).
R-024 · Before trusting `list_migrations`/migration history as "what's actually applied," diff it against the real schema (`list_tables` verbose) — this project's `0012`–`0017` were live on the schema but absent from tracked history (applied manually, outside the CLI, at some point).
R-025 · Never link straight to a Supabase Storage signed URL with `<a href download>` for a real download button · the `download` attribute is ignored by browsers for cross-origin URLs (Storage's domain differs from the app's), so it just navigates/opens a tab instead of downloading — use `downloadFile()` (`src/lib/utils.ts`, fetch-as-blob + temporary anchor) instead.
R-026 · The Settings/Profile page's URL is `/profile` (`src/app/profile`), not `/settings` · renamed D-017; update `src/middleware.ts`'s `PROTECTED_PATHS` and `AppShell.tsx`'s nav together if it ever moves again.
R-036 · `middleware.ts` must live at `src/middleware.ts`, not the project root · this project uses a `src/app` router; Next.js silently never invokes a root-level middleware file when `src/` is in use — no build error, no runtime error, protected routes just stop being gated. Cost a full session as D-008 before the misplaced file was found.
R-027 · `generations.output_url` is never actually persisted — it's a private-bucket signed URL that expires, so any query returning generations to a client must call `signGenerationOutputs()` (`src/lib/projects.ts`) on the result first, never trust the raw DB column · `getProjectDetail` and `/api/projects` both selected the always-null column directly until this was caught (Project grid/detail pages showed no thumbnail, disabled Download) — `generation.ts`'s own `signUrl()` calls were the only place doing this correctly before.
R-028 · Never run `next build` for local verification — use `tsc --noEmit` + `eslint` only · `next build` shares `.next` with a running `next dev` server and corrupts its cache/manifests, forcing a manual `.next` wipe to recover (this is what was happening to the user repeatedly before this rule).
R-029 · Any client data shown in more than one independently-mounted component (e.g. `AppShell`'s sidebar/header + a page's own display) must go through the shared `@tanstack/react-query` cache (`src/hooks/use-profile.ts`'s `useProfile`/`useUpdateProfileCache` pattern), not a per-component `useState` + `fetch` · two independent copies only sync on their own next mount (looked like "have to navigate away and back" to the user) — react-query's shared cache key updates every subscriber immediately. `react-query` was already an installed dependency with a `QueryClientProvider` at the root but unused until this.
R-030 · Avatar photos upload through `/api/uploads/sign` + `/api/uploads/confirm` with `kind: "avatar"`, reusing the `brand-logos` bucket at path `{user_id}/avatar/{timestamp}-{filename}` — no new bucket/migration · that bucket's RLS only checks the first path segment (`auth.uid()`), same reasoning as brand-logo/R-018; `confirm` writes the public URL straight to `profiles.avatar_url`.
R-031 · Every full-script write (first-time `/api/scripts/generate`, `/api/scripts/[id]/regenerate` for plain Regenerate + language/subtitle changes) must go through `writeScript()` (`src/lib/scripts.ts`), never call `generateMasterScript`/`masterScriptPrompt` directly from a route · a prior direct call in `generate/route.ts` had drifted from `regenerate`'s prompt, so first-time scripts came back without the structured scene-by-scene format regeneration produced — `writeScript()` is now the sole call site, so both paths are byte-for-byte identical by construction, not by convention.
R-032 · A custom (user-typed) idea keeps `style: "custom"` all the way into the `scripts.style` column instead of being overwritten by whatever style Gemini's response classified the body as · lets `regenerate/route.ts` correctly reconstruct the original idea shape from the stored row on a later regenerate.
R-033 · `masterScriptPrompt`'s language instruction must name every field that has to be translated (`title`, `hook`, `cta`, `scene_descriptions`, `emotional_direction`, body's DIALOGUE/SUBTITLE lines) explicitly, and the body's header line must be model-written, not `${idea.title}/${idea.hook}` string-interpolated · a vague "write every spoken line... in X" instruction left `title`/`hook`/the body header verbatim in English (the model just echoed the English idea context back) while `cta`/`scene_descriptions`/dialogue did translate — confirmed live for `bn`/`hi` before and after the fix. Only structural labels/camera-blocking directions (CONTINUITY LOCK, CAMERA:/ACTION:/AUDIO:, SCENE/FINAL FRAME/VIDEO STYLE headers) stay in English by design — those are director's notes for the video generator, not viewer-facing text.
R-034 · The Gemini API key in `.env` is on the free tier — hard-capped at 20 `generateContent` calls/day for whatever model `GEMINI_MODEL` points to, returning a 429 `RESOURCE_EXHAUSTED` once hit · easy to exhaust just from live-verification testing (happened twice this session); a 429 here surfaces to the user as a failed/silently-stuck script generation or regenerate, not a formatting bug — check this before assuming a code-level cause when generation stops working. No code fix possible; needs a paid tier or waiting for the daily reset (Google's stated retry-after is a short backoff hint, not the real daily reset time).
R-037 · `brand_profiles.logo_path` is a storage path, not a fetchable URL (the column literally named `logo_url` doesn't exist — don't assume it does) · every consumer must build the public URL itself: client-side via `supabase.storage.from("brand-logos").getPublicUrl(path)`, server-side (no supabase client in scope, e.g. `gemini.ts`) via `${NEXT_PUBLIC_SUPABASE_URL}/storage/v1/object/public/brand-logos/${logo_path}` since that bucket is public (R-018).
R-038 · Script-writing Gemini calls (`generateScripts`/`generateScriptIdeas`/`generateMasterScript`) attach the brand's actual logo image as a multimodal Part (`scriptContents()`/`brandLogoPart()` in `gemini.ts`) whenever `logo_path` is set, so the FINAL FRAME's on-screen brand text/logo describes the real logo instead of inventing one · previously the logo was never mentioned anywhere in any prompt, so on-screen branding was pure hallucination and varied every generation — `brandBrief()`'s logo line in `prompts.ts` must stay in sync with whether the image was actually attached, don't just add the text claim without the real Part.
R-039 · `BrandProfileDialog.tsx` (shared verbatim between `/profile` and the dashboard Upload step) manages "Brand Context Images" (`brand_profiles.context_image_paths text[]`) via: `/api/uploads/confirm` with `kind: "context_image"` *appends* one path to the array (read-modify-write); removing an already-saved image before Save goes through `PATCH /api/brand-profiles/[id]` with `contextImagePaths` as a full-array replace, not a per-item delete endpoint · no dedicated remove-one-image route exists by design — the dialog always sends the whole intended array back on save (was D-019, browser/API-verified 2026-08-11).
R-040 · The brand logo is sent to Seedance (via OpenRouter) as an actual `input_references` reference image on submit (`generation.ts` → `seedance.ts`, only when `brand.logo_path` is set), not just described in the script text · previously only Gemini's script-writing calls ever saw the logo (R-038) — the video-gen call itself had nothing but a text description to work from; uses the new `publicStorageUrl()` helper in `storage.ts` (was D-020).
R-041 · Website scanning is fully removed from the app, not just hidden — no `brand_profiles.website_url`/`website_summary` columns, no `src/lib/website.ts`/`fetchWebsiteText`, no references in either `/api/brand-profiles` route or `prompts.ts`'s `brandBrief()` · don't reintroduce a website-link field without a fresh decision; confirmed via full-tree grep before deletion, no RLS policy depended on either column (was D-021).
R-042 · Middleware page-level auth gating (`src/middleware.ts`, `PROTECTED_PATHS`) now correctly redirects every bare protected path (`/dashboard`, `/projects`, `/history`, `/credits`, `/profile`) to `/login` for an unauthenticated request — the earlier gap (D-008, filed 2026-07-29) is resolved, most likely by the `src/`-relocation fix in R-036 · re-verified live 2026-08-11 via curl; if this regresses, suspect `middleware.ts` moving out of `src/` again before anything else.
R-044 · `src/lib/providers/seedance.ts`'s model is chosen per-call by `modelFor(durationSeconds)` (15s → 2.0-fast, else 2.5), not a single constant · credits.ts's `costFor` rate table is split the same way (`CREDIT_RATE_15S`/`CREDIT_RATE_30S`) since the two models have meaningfully different real cost (D-022) — keep both switches in sync if a third duration/model is ever added.
R-045 · A DB check constraint's real name isn't always `<table>_<column>_check` even for an unnamed inline `check (...)` — confirmed via `pg_get_constraintdef`/`pg_constraint` against the live project before writing a migration that drops one by name · `list_migrations` alone can't be trusted for this either, migration history has known drift from the real schema (R-024) — query the live DB, don't infer from the source migration file.
R-046 · `contact_submissions` (Custom-plan "Contact Us", D-023) has RLS enabled but zero policies by design — every access path (`POST /api/contact`, `GET`/`PATCH /api/admin/contact-submissions`) goes through the service-role client, same as `error_logs` · a submission has no natural RLS owner (submitter may be anonymous), so this was the deliberate choice over adding an insert-anyone policy.
R-043 · To smoke-test an authenticated Next.js API route without a browser: create a disposable Supabase auth user via the service-role client (`admin.auth.admin.createUser({ email_confirm: true })`), sign in with `signInWithPassword` to get a `Session`, then build the cookie `@supabase/ssr` expects yourself — name `sb-<project-ref>-auth-token` (ref = the Supabase URL's subdomain), value `"base64-" + base64url(JSON.stringify(session))` (matches `cookieEncoding: "base64url"`, the library default) — and send it as a plain `Cookie` header with `fetch`/`curl`. `requireUser()` (`src/lib/auth.ts`) is cookie-only, no `Authorization: Bearer` fallback, so this is the only way to hit session-gated routes headlessly. Clean up afterward: delete the DB rows, `storage.remove()` any uploaded objects (a plain row/user delete does *not* remove them — confirmed leftover files after a first pass), then `admin.auth.admin.deleteUser()`.
R-047 · The public v1 API (`/api/v1/commercials`) creates a one-off, non-default `brand_profiles` row per call rather than reusing a caller's dashboard profile, and never persists the idea-step/30s script variant — `POST /api/scripts/generate` only ever writes the 15s master script now · both are permanent simplifications of the public one-shot contract (D-011/D-012, 2026-08-01), not bugs.
R-048 · Migration `0019`'s brand-profile backfill deliberately did NOT consolidate a user's multiple pre-existing profiles into one — each old project-scoped row became its own profile, only the most-recently-created marked default (D-013) · don't "clean up" apparent duplicate brand profiles from before that migration without checking they aren't genuinely different brands.
R-049 · Brand logo/context-image uploads reuse `/api/uploads/sign`+`/api/uploads/confirm` (widened to accept `brandProfileId`) rather than dedicated brand-profile upload routes (D-015) · that bucket's RLS only ever checked the path's first segment, so the existing routes already didn't care what the second segment meant.
R-050 · `profiles.avatar_url` is editable through `/api/profile` as a plain URL field (no dedicated upload endpoint) — same pattern as the removed `website_url` field before it (D-018) · if a real avatar-upload flow is ever built, it still confirms/writes through this same field, not a new column.
R-051 · `src/lib/providers/seedance.ts`'s model is chosen per-call by `modelFor(durationSeconds)` (15s → 2.0-fast, else 2.5), not a single constant · credits.ts's `costFor` rate table is split the same way (`CREDIT_RATE_15S`/`CREDIT_RATE_30S`) since the two models have meaningfully different real cost (D-022) — keep both switches in sync if a third duration/model is ever added.
R-052 · Billing (Dodo Payments, D-026) is one-time-payment products per 30-day period, NOT Dodo's native Subscription object — `profiles.plan`/`plan_period_end`/`plan_grace_end` are the actual source of truth, set only by the `dodo-webhook` Supabase Edge Function on `payment.succeeded` · never trust a Dodo subscription webhook/status here, this app doesn't use that object at all; checkout itself is a normal Next.js route (`POST /api/billing/checkout`, session-authed) since only the webhook/cron pieces needed to be Edge Functions (R-054).
R-053 · Every `payment.succeeded` resets (not tops up) `profiles.credits_balance` to exactly `PLAN_CONFIG[plan].credits` via a computed signed delta through the `spend_credits` RPC — never top-up/rollover (D-022 extended to billing renewals) · the delta math lives in `dodo-webhook`'s own code (Deno, can't import `src/lib/credits.ts`), hand-kept in sync with `src/lib/payments/plans.ts`'s `PLAN_CONFIG`.
R-054 · `dodo-webhook` and `expire-subscriptions` are Supabase Edge Functions (`supabase/functions/*`), not Next.js routes (D-029) — deployed live via the Supabase MCP's `deploy_edge_function`, source also committed to the repo for history/review but the deploy is the actual live artifact, not a build step off the committed file · `supabase/functions` is excluded from the root `tsconfig.json` (Deno globals/`npm:`/`jsr:` specifiers don't resolve under the Next.js Node config) — a third Edge Function needs the same exclude, it's already glob-covered by the existing `supabase/functions` exclude entry.
R-055 · `expire-subscriptions` (the grace-period downgrade sweep) is scheduled via `pg_cron`+`pg_net` (migration `0029`), calling the Edge Function's URL with `NEXT_PUBLIC_SUPABASE_ANON_KEY` as the bearer token — safe to commit literally in the migration since that key is already public (shipped in every browser bundle) · `verify_jwt: true` is kept on the function itself (any valid Supabase JWT passes, including anon) because the sweep is idempotent/self-limiting — it only ever touches rows objectively already past their real `plan_grace_end` timestamp, so triggering it extra often or by anyone holding the anon key is harmless.
R-056 · `profiles` no longer has a blanket UPDATE grant for `authenticated` — as of migration `0028`, only `full_name`/`username`/`avatar_url` are grantable (matches `/api/profile`'s `EDITABLE_FIELDS`), enforced at the Postgres column-privilege level, not just RLS row-visibility (D-028) · adding a new self-editable profile field needs BOTH `EDITABLE_FIELDS` in `/api/profile/route.ts` AND a `grant update (...)` migration, or the field will silently 403/fail for direct-client writes; `spend_credits` (security definer) and the service-role key are unaffected by this grant either way.
R-057 · The Dodo Node SDK is installed as a real dependency (`node_modules/dodopayments`) — its `.d.ts` files under `resources/*` are the authoritative source for exact field/method names (`payment.total_amount`, `payment.product_cart[].product_id`, `client.checkoutSessions.create`, `client.webhooks.unwrap`, etc.), more reliable than WebFetch summaries of the hosted docs, which were sometimes incomplete or wrong (e.g. claimed the Payments list response "lacks product-level detail" — the actual type has `product_cart`) · grep the installed package before trusting a docs fetch for any future Dodo work.
